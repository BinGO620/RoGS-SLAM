## 头号假设（A1）

`DynamicKeyframe.gap_cap=5` 强制每 5 帧插一个 KF：实测 **215 KF / 1074 帧**，正好 1/5。
vanilla 按 `kf_overlap=0.9` / `kf_translation=0.08m` 决定，而本序列帧间平移中位仅 **0.65cm**
（要 12 帧才够 8cm）⇒ vanilla 的 KF 少一个量级。

⇒ 地图长期欠优化 ⇒ frame 371 平移突增、新几何进视野时撑不住。

一条假设同时解释：sync 修好、w≡1 无效、vanilla 不崩、双稳态、崩点固定在 371。

## 最终判决（2026-08-18 定稿，n=5 后。判据未改，但 n=2 的读数被 n=3/n=5 部分推翻）

### 完整逃逸账（f3_st_hf，async，逃逸 ≡ ATE < 5cm）

| 臂 | KF | 逃逸 | 逐 run ATE |
|---|---|---|---|
| control（RS 全开） | 215 | 0/4 | 35.29 / 36.09 / 35.16 / 35.52 |
| w≡1（RS 跟踪通道切断） | 215 | 0/1 | 35.99 |
| −RobustTracking | 215 | 0/2 | 36.12 / 35.71 |
| −DeferredCommit | 215 | 0/2 | 36.05 / 34.13 |
| **小计「215KF + RS 有效」** | | **0 / 9** | 全部 34-36，全崩在 frame 371 |
| −DynamicKeyframe | **57** | **2/3** | 4.01 ✅ / 2.91 ✅ / **25.02 ❌** |
| A5 bothoff（RS 双通道均切断） | 215 | **3/5** | 2.19 ✅ / 35.36 ❌ / 2.38 ✅ / 2.45 ✅ / **18.95 ❌** |
| −ReliabilitySignal（整个） | 215 | 2/2 | 2.15 ✅ / 2.39 ✅ |
| **vanilla** | 稀疏 | **4/5** | 2.51 / 2.44 / 2.33 / 2.18 ✅ / **20.94 ❌** |

参考（sync，`iter_per_kf` 150 且后端不自由跑）：control **3.394** ✅、fix **3.189 / 3.460** ✅ ⇒ **3/3**。

### 判决

**1. ★ 定性必须改写：vanilla 自己也会崩（4/5）。**
`vanilla seed4 = 20.94`，发散区间 frame 299→409（vanilla 稀疏 KF 采样粗），**夹住 371**，同一失败点。
机器混杂已排查：2060 今日 12 个 f3_st_hf run 中 5 个逃逸，同一 fix 臂 2060 上 3/4、3090 上 1/2，
**无系统性偏差证据**。
⇒ **f3_st_hf 对 MonoGS 本身即临界序列（~20% 失败）。**
⇒ 我们不是「把稳定序列弄崩」，而是**把偶尔失败的序列变成必然失败的**（0/9）。
⇒ **目标随之改变：不追「稳定 2cm」，追「恢复到 vanilla 的失败率」。**

**2. 回归本身是硬的**：0/9 vs 4/5，Fisher 精确检验 **p < 0.001**。

**3. 无任何单一干预可保证修好**（全部只把逃逸率从 0 提上来，未消除双稳态）：
−DynKF 2/3、bothoff 3/5、−RelSig 2/2（n 小）。bothoff 3/5 与 vanilla 4/5 **统计上不可分**。

**4. A2 RobustTracking、A3 DeferredCommit 干净排除**（0/2，仍在 371 翻倍）。

**5. (a) vs (b) 倾向 (a)**：bothoff（RS 仍 enabled ⇒ 损失留在 soft 分支，仅切断两条输出通道）
从 0/9 提到 3/5 ⇒ 病因是**两条通道本身**，不是损失分支 artifact。
且 bothoff **保留了 215 密集 KF** 仍恢复 ⇒ `DynamicKeyframe` 并非必须动的那一个。

**6. FPS 不预测结果**（最快 A4 1.115 修好、最慢 A1 0.590 也修好、崩掉的 A2 居中 0.83-0.86）
⇒ 「地图预算随负载漂」的解释对 RS 这条不成立，撤回。

### 方法论记录（本批的教训）

`−DynamicKeyframe` 在 n=2 时是 2/2、看起来是干净修法；补到 n=3 变成 **2/3**。
用户定的「n=2 筛选、n=3 才是正式数」规矩**直接接住了这个假阳性**——
若按 n=2 收工，就会去改 `gap_cap` 并以为问题解决了。
本会话共有三个解释被自己的预注册判据推翻（见 `NEXT_SESSION_PROMPT.md §2`）。
